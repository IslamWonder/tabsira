# 20 · Prompts and search: where they live

A map of every model prompt in the code, and of how search finds the texts behind an insight, so the owners can review and change them in one place. Read-only inventory: it describes the code, it does not replace it. Keep it in step whenever a prompt file or a prompt constant changes.

**Phase:** 1 · **Priority:** High · **Status:** 🔄 · **Updated:** 2026-10-05 (Tunis)

## How prompts work

- A prompt is a text file `apps/api/src/pipeline/prompts/<name>.v<N>.txt`, loaded by `load_prompt()` in [prompt.py](../../apps/api/src/pipeline/prompt.py).
- **Changing what a prompt says means a new file with the next version** (`...v6.txt`), then pointing the `SYSTEM_PROMPT` / `USER_PROMPT` constant at it. Old versions stay in the folder as history. A result records `name@sha256`, so every answer names the exact text that produced it.
- Some prompts take values (`render(...)`, `string.Template`). The model never writes scripture: its output carries evidence ids only (AGENTS.md, Never).
- Prompts are English instructions for the model; user-visible text is Arabic and lives in the web messages modules, not here.

Since 2026-10-05 the production prompts hold **no example scene, no example query, no example insight and no scripture**: rules and data contracts only (the owners' brief of that day, §2). The scene analyzer's rules about a phone, a rug or a raised hand became general rules («an object at rest proves no use of it»); the planner receives neither the learner nor the learning units; the verifier is asked to test and reject, never to justify. Test cases live in `apps/api/tests` only.

Since decision 64 (task 22.2) the composer reads `learner_view()` of [composer.py](../../apps/api/src/pipeline/insight/composer.py): the profile fields the person declared (knowledge level, age range, religious background, goals), each left out while `unknown`, and nothing at all while personalization is off; never the gender. The explanation can be published, so composer v5 writes one neutral text that never lets anyone tell the reader's gender, religion or age: the profile changes only depth, vocabulary, sentence length and examples, and the address is always impersonal. The private chat gets the same fields plus a declared gender in its system prompt as `$learner` (`none` when empty); chat v6 may use gendered Arabic address only for a declared gender and never states or reveals the profile. With every field unknown the composer's payload is byte for byte the one sent before. Both prompts never judge the profile and keep every scripture rule of the version before.

## Where a prompt is checked

- [tests/test_prompt.py](../../apps/api/tests/test_prompt.py) covers loading and hashing.
- `make eval` (gold scenes, chat cases) is how a new version is compared with the last; results go in [docs/EVALUATION.md](../EVALUATION.md) (chat: v2 scored 9/12, v3 11/12).

## Changing a prompt

1. Copy the current file to the next version, edit the copy.
2. Point the constant at it; keep the old file.
3. Run the tests of the area (`uv run pytest -n 1 tests/<area>`) and `make eval`; note the scores in `docs/EVALUATION.md`.
4. Anything that touches what is shown as Quran or hadith, or the leak guards, gets the scripture-guardian review before commit.
5. Update this file in the same commit.

## How search works: from a scene to the texts behind an insight

Orchestrated by `PipelineInsightEngine` in [pipeline/insight/engine.py](../../apps/api/src/pipeline/insight/engine.py). Nothing a search returns is ever displayed as found: a result is ids, ranks, the channels that found them and the query that ranked them best. Scripture is loaded from the store by id afterwards (AGENTS.md, Never). Rebuilt on 2026-10-05 after the owners' brief (task 05.8): meanings are hypotheses before the search, the texts are tested after it, and the insight is written last.

### The flow

```text
scene (from the scene analyzer)
  1. UNDERSTAND  ontology constraints -> corpus check -> intent planner (LLM) -> up to 4 search intents,
                 each: scene anchors, observable meaning, concept to test, doubts, forbidden assumptions,
                 and per corpus: lexical queries (keywords) + semantic queries (one sentence)
  2. SEARCH      per intent, per corpus (Quran and hadith apart):
                   embed the sentences (one call; failure = RETRIEVAL_ERROR, never a lexical-only answer)
                   lexical queries -> full text + concepts; semantic queries -> vectors (50 each)
                   hadith: over the enriched Sunnah file first (3,920 sahih records matched to their
                   narrations in the nine books, one narration per record), the whole store only when
                   no record fits (§7, §12 of the brief; HADITH_SEARCH_SCOPE)
                   -> RRF, one weight per channel -> 120 kept -> reranker on the head (30) when on,
                   reading the intent's own sentence -> 12 per corpus to the verifier, each verse
                   with its neighbouring verses as context
  3. VERIFY      relevance verifier (LLM), one call per intent: accept/reject every text with its
                 relation, word positions, link, needed context, assumptions, reject reason; names the pair
                 the gate: decision 65 (an unruled hadith is shown as stored, a ruled-out one may be replaced in its tier), unseen before seen
                 no complete pair anywhere: the intents that found nothing go back to the planner with
                 the rejection reasons (same clues, same meaning, other words), two rounds at most
  4. COMPOSE     the server picks the learning unit and orders (focus, complete pair, relation, next step,
                 new texts); the composer (LLM) writes from the confirmed intent and the links;
                 the leak guard rejects scripture-like text; the trace is saved with the scan
```

Where the data comes from: the Quran (quranpedia, edition 2) and nine hadith books sit in the `corpus` schema; folded search copies in `quran_verse_search` and `hadith_search`; vectors in the `vectors` schema, one row per text, model and size (6,236 verses, 65,712 hadiths); concepts in `quran_annotations` and `hadith_signals`. Vectors are computed by `src.cli.embed_corpus`; a document's SHA-256 is stored with its vector, so a changed document is embedded again, that one only ([docs/EMBEDDINGS.md](../EMBEDDINGS.md)).

### What was measured (docs/BENCHMARK.md, retrieval)

- Embedding: `text-embedding-3-large` @ 1536 gives MRR@10 0.696 (OpenAI); `bge-m3` @ 1024 gives 0.601 (OVH).
- Full text MRR@10 0.219, trigram 0.133 (and 11 s p95), so trigram is unused.
- RRF of the three reaches recall@30 of 94 %, the most of any method, but ranks worse than the vector alone (MRR 0.564 against 0.696): that is the reason for the reranker.
- Rerank by `gpt-5.4-nano`: MRR 0.770, about 3 s. Cross-encoder `bge-reranker-v2-m3`: MRR 0.667, 19 s for 30 passages on this CPU.
- A scan takes about 22 s at p50 and 30 s at p95, about $0.02 (docs/EVALUATION.md).

### Where to improve later

Each lever says what to change and what to measure. Measure with `make benchmark` (retrieval section) and `make eval` before and after; record the numbers in docs/BENCHMARK.md and docs/EVALUATION.md.

| Lever                           | Why it may help                                                                                                                                          | Where                                                            |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Per-channel RRF weights         | Vector is the strongest single list (0.696) yet each channel weighs one; weighting vectors up could lift the fused MRR. Measure before changing.         | `channel_weights()` in search.py, `weights` argument of `fuse()` |
| The shortlist sizes             | 120 fused, 30 reranked, 12 verified are the brief's starting values; a right text at rank 13 to 120 is never judged. Cost is latency and tokens.         | `FUSED_TOP`, `RERANK_TOP`, `VERIFY_TOP`                          |
| Better queries from the planner | Retrieval can only find what the queries say. The planner now writes keyword and sentence queries apart; `make eval` judges the wording.                 | prompt `intent_planner_system`, task 05.8                        |
| Stemming and stop words         | Light stems only; no roots. Add synonyms, or root matching, if full text misses morphological variants.                                                  | [query.py](../../apps/api/src/retrieval/query.py)                |
| Richer documents                | The concepts are what let modern Arabic find old Arabic; more or better concepts for texts that have none (hadiths: about 7,000 of 65,712 have signals). | `hadith_signals`, `quran_annotations`, then re-embed             |
| Chunking of long hadiths        | A document is cut at 1,200 chars, keeping the start; a subject that appears later is missed.                                                             | `TEXT_MAX_CHARS` in documents.py                                 |
| A rerank model on OVH           | Without one an OVH scan keeps the fused order, which ranks worse.                                                                                        | `OvhSettings.rerank_model`, benchmark first                      |
| Cross-encoder on a GPU host     | Best quality-per-token if latency stops being the problem.                                                                                               | `RERANKER=cross_encoder`, services/vision                        |
| Gold scenes                     | Retrieval quality is judged on 15 scenes and the contest cases; more scenes with expected texts make a change provable.                                  | `apps/api/tests/evaluation/scenes/gold.json`                     |
