# The two candidate-source files and their contract

The owners' brief of 2026-10-05 (§7) names two files as the candidate source of the insight engine's search: `final_complete_verses_20251202_194512.json` (the annotated Quran) and `processed_sunnah_data.json` (the enriched Sunnah file, 3,920 records of a sahih compilation). This page says what each file holds, which stored field each part lands in, and how the five things the brief asks to keep apart are kept apart. The audited copies and their checksums are in [ASSET_MANIFEST.md](ASSET_MANIFEST.md); the import is in [CORPUS.md](CORPUS.md).

Neither file is ever displayed. The displayed verse comes from quranpedia's dump (decision 16) and the displayed hadith from the nine books as stored (decisions 17 and 64); both are read by id, byte for byte, with their stored hash.

## The annotated Quran (6,236 verses)

| The brief asks to separate      | Where it is                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The original text               | Not taken from this file: the verse text is quranpedia's, in `corpus.quran_verses.text` with `text_sha256`; the file's `text_ar` is read at import only to refuse annotation strings that repeat it.                                                                                                                                                                    |
| The search text                 | `corpus.quran_verse_search.normalized_text` (folded: no diacritics, unified alif, hamza seats, yeh, teh marbuta; negation, conditions and every meaningful word kept) and `guard_text` for the leak guard.                                                                                                                                                              |
| The reference data              | `surah`, `ayah`, and quranpedia's `quranpedia_ayah_id`, joined by surah and verse number (`source_ayah_id` keeps the file's own id).                                                                                                                                                                                                                                    |
| The context or documented gloss | The model-written annotation (`islamic_domain`, `categories`, `key_concepts`, `keywords_ar`, `semantic_tags`, the whole `annotation` object) in `corpus.quran_annotations`: a ranking signal, never a gloss shown and never the basis of relevance on its own. The verse's context at evaluation is its neighbours in the surah, read from the store (`quran_context`). |
| The source identity and version | `source_sha256` of the file and `annotation_model` (the model that wrote it); the verse text carries quranpedia's `source_version`.                                                                                                                                                                                                                                     |

Every verse is a unit with a fixed identity (surah, ayah). The verifier reads the verse's folded text and, apart from it, the folded verse before and after it (`context`), so the verse's own words are judged and the neighbours only help read them.

## The enriched Sunnah file (3,920 records)

| The brief asks to separate      | Where it is                                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| The original text               | The record's own narration (`original_text`, an abridged compilation's wording) is not stored. At import it is folded and matched to its narrations in the nine books by word 3-gram coverage; the stored narration (`corpus.hadiths.text`, with `text_sha256`) is the original text the engine uses, byte for byte, so the identity of what is shown is always a real narration of a real book (§12). |
| The search text                 | `corpus.hadith_search.normalized_text` of each matched narration, with the chain of narrators cut from the retrieval document and the words kept whole (`documents.hadith_body`).                                                                                                                                                                                                                      |
| The reference data              | The compiler's own citations («[خ 8، م 16]») decide which book's narration is the record's best match; every match is kept in `hadith_signals.matches` (`hadith_id`, `coverage`, `cited`) and the best one in `hadith_id`.                                                                                                                                                                             |
| The context or documented gloss | `semantic_tags`, `key_concepts`, `topics_for_retrieval`, `domain`, `category_*`, `sciences`: model-written ranking signals in `corpus.hadith_signals`. `model_written_summary` and `model_written_rephrase` are stored under names that say a model wrote them and are used by nothing (§7: a generated gloss without a source is never the basis of relevance).                                       |
| The source identity and version | `source_record_id` (the file's `id`), `source_sha256` of the audited file, `generated_by_model`.                                                                                                                                                                                                                                                                                                       |

### How the search uses it (§7, §12)

- With `HADITH_SEARCH_SCOPE=enriched_first` (the default) the hadith candidate pool is the set of narrations the records match (`hadith_records`: narration id → record id). The full-text, concept and vector lists are narrowed to it, and the fused list keeps one narration per record, the best ranked, so the parallels of one hadith never fill the shortlist.
- The narration kept is what the verifier judges and what is shown: another narration of the same record is the same hadith in another book and keeps its own identity (book, number); nothing is composed from two narrations.
- When the gate keeps no hadith for an intent, the same queries run over the whole store (65,712 narrations), the narrations of the records already judged left out, and one more verifier call judges the widened candidates alone. `HADITH_SEARCH_SCOPE=all` searches the whole store at once.
- Every candidate in the scan trace names its record (`record`), so a shown hadith can be followed back to the record that proposed it.

## The embedding and the index

Vectors are computed on the retrieval document (folded text, then the concepts of the record or annotation), one row per text, model and size, keyed by model name and dimensions, with the document's SHA-256 stored beside the vector (docs/EMBEDDINGS.md). A query is embedded with the same model and size (`embedding_model`, `embedding_dimensions`), and the store is checked at start to hold vectors of that model; vectors of another model or size are never mixed (§7).
