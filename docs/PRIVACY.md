# Privacy: what the API stores

This is the working inventory behind the terms and privacy page. It is updated in the same change as any new data flow, and the public page must say nothing this file does not.

## Accounts

The `app` schema stores, per account and for these reasons only. `users`: the e-mail address (lower-cased; to sign in and to send the two account mails), a bcrypt hash of the password or nothing for a Google-only account, the display name, the active and admin flags, the time the address was verified, and the creation, update and deletion times. `oauth_accounts`: the provider name and Google's stable subject id, to recognise the same person next time; no Google tokens, picture or profile are kept. `sessions`: the SHA-256 hash of the session cookie's random token, the user, the creation, last-seen and expiry times, a keyed hash of the IP address (never the address) and the browser's user agent cut to 256 characters, so a person can see and end their sessions and a stolen database cannot be replayed as a cookie. `profiles`, one per account and optional: the goals, prior knowledge and age range the person chose, their religious background and gender (set in the settings only), the language, the personalization, memory and photo-storage switches, the theme, the motion preference (`system`, `on` or `off`, a display setting that follows the account to its other devices and is part of `GET /account/export`), the sound switch and the version of the consent text last answered; every unanswered field is `unknown` and nothing is inferred from a photo, a name, a place or behaviour; there is no birth date. The religious background, the gender and the age range are private: they are returned only to their owner, by `GET /profile` and `GET /account/export`, and are never written to a log. `consents`: an append-only history of each consent given or withdrawn, with its kind (`terms` for the terms of use, `privacy` for the privacy policy, and the three switches), the version of the text and the time, as the record that the person agreed. Signing up writes the `terms` and `privacy` rows at the versions accepted (decision 35); a Google sign-up keeps the versions ticked in `oauth_states` for a few minutes until the callback. `email_tokens`: the SHA-256 hash of each mailed verification or reset link token, the address it was sent to and its expiry, used once. `login_attempts`: keyed hashes of the IP address and of the e-mail address of each sign-in, sign-up and mail request, for rate limiting only, over a window of 15 minutes by default. `oauth_states`: the short-lived state of a Google sign-in in flight, valid for 10 minutes and deleted when used. Expired sessions, tokens, attempts and states are deleted by the next write to their table, not by a scheduled job, so on a quiet system an expired row can remain until then. `GET /account/export` returns everything an account owns as JSON, and `DELETE /account` deletes the account and every row above that belongs to it, sessions included.

Signing up with Google from the sign-up page needs the terms and privacy box ticked first. The tick is kept only in that tab's `sessionStorage` (the versions ticked and the time), is used once when the person comes back from Google to record the acceptance through `POST /auth/legal/accept`, and is discarded after ten minutes; it never travels in a link.

## Account mail and Google

Two flows send an address outside our servers, and only for account purposes. The API sends the verification and password-reset mails, and nothing else, through the SMTP server named by `SMTP_HOST`; that server receives the recipient's address, their display name and the link in the mail. The link carries its token after a `#`, so it appears in no web server log. Signing in with Google sends the browser to Google and receives from Google, after the person agrees, the subject id, the e-mail address with its verified flag and the name. No analytics, tracker or third-party script is involved in either flow.

## Learning path and ontology

Two more tables of the `app` schema, and what each one keeps. `learner_unit_states`: for one account (its id) or one guest (an opaque random key the browser holds, never a name or an address) and one unit of the learning path, how many times an insight of that unit was shown, opened and completed (the person pressed «تمّ»), and the time of the first and the last of these. Completed means completed: it is not a score, a level or a measure of what the person knows or believes, and none of those is stored. «تمّ» (`POST /insights/{id}/complete`) counts a completion there, unless the person switched memory off; `GET /account/export` returns these rows, `DELETE /account` deletes them with the account (`ON DELETE CASCADE`), and a guest's rows are added to the account's at the first sign-in. `ontology_candidates`: the labels and concepts that a detector or a model proposed and that the world ontology does not hold, each with how many times it came up, which stage proposed it (detector, vision model or planner) and up to five short examples of model-written context, such as a scene description, so an editor can decide whether to add the term to a new version of the ontology. No account, session, photo, location or text typed by a person is stored in it, and a sensitive scene contributes no example.

## Error reports

When `GLITCHTIP_DSN` is set, the API sends error reports to the GlitchTip server it names, and sends nothing when it is empty. This is the only flow of this kind, and it leaves from our servers: the visitor's browser makes no request to GlitchTip, because the web app posts its errors to the API's own `POST /client-errors`, which forwards them. A report holds the type and stack frames of the failing code, the route pattern (`GET /scripture/quran/{surah}`, never the path with its ids), the page address of a browser report, the release and environment names, the browser family (`chrome`, `firefox`, `safari` and a few others, never the full user agent), a request id and the time. Before it leaves, everything is cleaned (`docs/ERROR_TRACKING.md`): no request body, cookie, query string, `Authorization` header, address or user id; no local variables; the value of any field named like a secret, a profile field, a photo or a location is replaced; every Arabic text, so no verse, hadith, display name or typed text, is replaced; and an event raised under `/scripture` keeps only its type, frames and route. `POST /client-errors` needs no sign-in, so it stores nothing about the sender: the per-address limit counts a keyed hash of the address in the memory of the worker for five minutes and keeps it nowhere else. No account row refers to a report, so `GET /account/export` and `DELETE /account` have nothing to add for it. GlitchTip keeps reports for as long as its own retention setting says, which the operator sets and the privacy page must state.

## Cookie consent

Decision 32. The visitor chooses on the first visit, signed in or not, and the API keeps the proof of the choice in one more table of the `app` schema. `cookie_consents` holds one row per choice: a random id of the browser (`consent_id`, made by the server and kept by the browser in a first-party cookie; it is not derived from anything about the person), the version of the cookie policy the visitor was shown, whether each category was accepted (`necessary` is always true; `analytics` and `behaviour` are chosen separately), the browser family only (`chrome`, `firefox`, `safari`, `edge`, `opera`, `samsung_internet` or `other`; the database refuses anything longer or different, so no full user agent can be stored), the time, and the account id when the visitor was signed in, so the choice can be shown in «ملفي». No IP address is stored, not even hashed. The table is append-only: choosing again adds a row and the latest row of an id is the choice in force; a database trigger refuses an update, a delete and a truncate, except the delete that removes a user's rows when the user's account is deleted. `GET /account/export` lists, under `cookie_consents`, every choice made while signed in, and `DELETE /account` removes those rows with the account. Rows made while signed out carry no account and cannot be tied to a person, so the export does not list them and the deletion does not remove them.

A choice lapses, and the visitor is asked again, when `COOKIE_POLICY_VERSION` changes or after `CONSENT_REASK_DAYS` (182, six months). Until then the API reports the categories as chosen; after, only the necessary one is on and `reask` is true. The three routes, none of which needs a sign-in: `GET /consent/policy` (the policy version, the three categories with their Arabic titles and descriptions, from `src/messages.py`, and the re-ask interval), `POST /consent` (records a choice and returns the consent id with what is in force) and `GET /consent/{consent_id}` (what an id's latest choice allows now). The consent id is the only handle on a record and is unguessable (122 random bits); whoever holds it can read that choice and add another, which is why only the browser that was given it should keep it. `POST /consent` is limited per address and over all addresses, counted in the memory of each worker for five minutes and kept nowhere else, and refuses a body over 4 KiB. The responses carry `Cache-Control: no-store`. The web app's cookie for the id is itself a necessary cookie: it must hold the id and nothing else, and no analytics or behaviour tool may start before its category is accepted.

No retention period is set yet. The table is append-only by design, so nothing deletes old rows; the owners decide how long proof of consent is kept before launch, and the job that applies it must be the one thing allowed to lift the guard. The privacy page must name this table, the reasons above and that period.

In the browser, the consent uses three first-party cookies and nothing else, none readable by another site: `tabsira_consent` holds the consent id the API gave and nothing about the choice or the person, for 395 days, so the choice is found again; `tabsira_consent_dismissed` remembers, for the browser session only, a refusal the API could not record, so the question is not put on every page; `tabsira_consent_view` tells a visitor without JavaScript which view of the screen to show after the form posted (customise, or a failed save), for five minutes. To render the consent screen already open in the first paint, the web server reads `tabsira_consent` and asks the API (`GET /consent/{consent_id}`) what that id allows, once per page request; that request carries the visitor's session cookie when there is one, because a choice made while signed in is tied to the account. A form posted without JavaScript reaches the API from the web server, so those posts share the server's rate-limit budget. No analytics or behaviour script is loaded before its category is accepted, and Consent Mode starts with every category denied.

## Analytics and heatmaps

Both tools are configured on the web server (`GA_MEASUREMENT_ID`, `CLARITY_PROJECT_ID`), read at request time; empty means the tool does not exist for the visitor. Each is injected by the browser only after its category is accepted (`analytics` for Google, `behaviour` for Clarity), and neither runs on `/admin`, `/dev`, sign-in, sign-up, the mailed-link pages or `/me`.

- **Google Analytics 4** receives the page path without query string or fragment, the page title, the referrer's origin without its path, what Google itself derives from the request (browser, device, language, approximate region from the IP address), and Enhanced Measurement (scrolls, outbound clicks). Google signals and ad personalisation are off. Product events carry fixed words, counts and booleans only (typed in `apps/web/src/analytics/events.ts`; a string that is not a short lowercase word is dropped): scan started and finished, insight opened, «تمّ» pressed, share, sign-up completed, consent changed. Nothing about a person, no text, no scripture, no location. An event raised on a page where no tool runs (sign-up) waits in memory and goes out on the next page that allows one; it is never written to storage.
- **Microsoft Clarity** receives clicks, scrolls, pointer movement, screen recordings and heatmaps. The whole `<body>` carries `data-clarity-mask`, so every text, every input and every scripture or user text is masked; Clarity's advertising storage is denied.
- **Withdrawal** stops both tools at once, denies Consent Mode storage, and deletes the `_ga*`, `_gid`, `_gat*`, `_clck` and `_clsk` cookies on the host and its parent domains. A consent change is reported to Google only while analytics stays accepted.
- Google and Microsoft are recipients of these data after consent; the privacy page lists them in «ما تستلمه أدوات القياس ومتى».

## Photos

Decisions 8 and 19, and section 19 of the master prompt. No route stores a photo yet. This is what `apps/api/src/services/image_service.py` and `apps/api/src/storage/` enforce, and what the routes that come next must keep. A photo sent for analysis is not stored by that: it stays at most an hour in the temporary store described under «Photos and scans», and never for a sensitive scene.

A photo is kept only when all of these hold, each a required argument the caller must state (`PhotoFacts`, `apps/api/src/storage/photos.py`): the feature `FEATURE_PHOTO_STORAGE` is on; the person is signed in (a guest's photo is never kept); the account has switched photo storage on (`profiles.photo_storage_consent`); the account did not say its age range is under 13 (an unanswered age is never guessed from a photo or anything else); and the scene is not sensitive. When any of them fails, the storage is not asked for anything and nothing is written. A photo is published only under the same conditions, checked again at that moment, so a photo of someone who has since said they are under 13, or withdrawn their consent, cannot be published.

Before a photo is kept, its file is read once for what the camera recorded: the GPS position, its accuracy and time, and the moment the photo was taken (`CaptureMetadata`, source `photo_exif`). That is private capture metadata for the owner, who confirms or changes the place; it is not part of the stored image, and its values are left out of its printed form, so it cannot reach a log line or an error report by being printed. Then the image is re-encoded as a new JPEG, upright, at most 2560 pixels on the longer side, with no metadata at all: no EXIF, GPS, XMP, IPTC, maker note, comment, thumbnail, serial number or ICC profile (a profile is applied to the pixels, which become sRGB, and then dropped). The check in the tests looks for each of these in the bytes that are stored.

The kept copy is one private object, `private/<128 random bits>.jpg`, in a private S3-compatible bucket (`STORAGE_BACKEND=s3`; production requires it and refuses to start without a usable bucket, decision 44) or, on a development machine with no bucket, under `data/media` on local disk (never committed). The key says nothing about the person or the photo. Its owner sees it through a link signed for `SIGNED_URL_TTL_SECONDS` (300 seconds by default, 3600 at most), and nobody else can read it. When the owner publishes, the object is copied to `public/<another random id>.jpg`, which is the only prefix served to the public, from `S3_PUBLIC_BASE_URL` (a CDN, or a bucket policy that makes `public/*` and nothing else readable); withdrawing, or removing the account's photos, deletes it. The code never marks an object public: what is readable by anyone is decided by the `public/` prefix alone, which the operator must set up and check. Private objects carry `Cache-Control: private, no-store`; published ones carry `Cache-Control: public, max-age=300`, never `immutable`, so a withdrawn or deleted photo can stay in browser and CDN caches for up to five minutes.

The S3 provider holds these objects as a processor, and it receives nothing else of ours: not the account, not the position, not the owner's name. The table that first stores a photo's key must add it to `GET /account/export`, and `DELETE /account` must delete its objects before the account row (`apps/api/src/services/account_service.py` says so); this paragraph is checked in that change.

## Admin area

Who may sign in, what they can see, and what is written down about them (`docs/ADMIN.md`). Three tables of the `app` schema. `admin_sessions`: one row per signed-in admin browser, with the SHA-256 hash of the cookie's random token, the account, the creation, last-seen and expiry times (twelve hours, never extended), a keyed hash of the IP address (never the address) and the user agent cut to 256 characters; deleted when it expires, when the admin signs out and with the account. `admin_totp`: the second factor of an admin, with the shared secret **encrypted** under `ADMIN_TOTP_ENCRYPTION_KEY` (a copy of the table is useless without the key), ten recovery codes as keyed hashes, when the factor was switched on and the step of the last accepted code so that a code works once; deleted when the admin switches it off and with the account. `admin_audit_log`: one row for every admin sign-in, failed sign-in and sign-out, every list page, record page, create, edit, delete and bulk action, every second-factor change, and every grant or revoke of admin rights done on the command line; a row holds the time, the admin's account id (for a failed sign-in, the account the attempt named, when it matched one), the action, the view and record id, a small JSON, a keyed hash of the IP address and the user agent. The JSON holds only the names of the fields that changed, a reason code and the ids a bulk action touched with their count: never what was typed, never a search word, never the e-mail address entered at a failed sign-in. The log is a TimescaleDB hypertable partitioned on its time column. It is append-only (a trigger refuses every update and delete), compressed after `ADMIN_AUDIT_COMPRESS_AFTER_DAYS` (30 by default) and dropped after `ADMIN_AUDIT_RETENTION_DAYS` (400 by default). Its account and record ids are plain columns with no foreign key: deleting an account does not delete its rows from the log, which keep an id that names nobody until the retention drops them, as the record of what an admin did.

What an admin sees of a person: the e-mail address, the display name, whether the account is active, an admin and verified, when it was created, updated and (if deleted) deleted, the consents given and withdrawn, and the browser's user agent of each session. An admin can rename an account, switch it on or off and end its sessions. An admin never sees a profile (religious background, gender, age range, goals, knowledge level), a password hash, a session token, a second-factor secret or recovery code, a photo or a location, and the admin area has no export: no CSV or JSON copy of this data can be made from it. Only a person with an account that has `is_admin` can sign in, with a password and, once enrolled, a code; admin rights are given and taken only on the server's command line.

## The social network

What «تبصرة تواصل» stores and shows (`docs/SOCIAL_NETWORK.md`). Everything below belongs to one account, is returned to its owner by `GET /account/export` (the `social` object) and is deleted with the account, except the moderation log. `users.handle` and `users.public_name`: the handle and the name the person chose to be known by on the network, both empty until they choose; they are the **only** things a public page says about a person, besides the month the account was created and three counts. The account's own display name, the e-mail address, the profile answers and any location are never in a public response, a feed, a comment or the sitemap, and the public name is never copied from the account's own name. `follows` and `blocks`: who follows and who blocked whom, with the time; a block is visible to its owner alone, and the blocked person is answered as if the other did not exist. `insight_publications`: the copy of a verified insight that a post publishes, made once and never edited (the database refuses an update): the platform's title, glimpse, explanation excerpt and small step, the insight's id and version, and **references** to the evidence (surah and ayah, book and hadith number), never scripture, which a reader's response reads from the scripture store. It keeps a photo reference only if the owner consented to publish the photo, the scene is not sensitive and the photo rules above still allow it at that moment (the feature is on, the account has not since said it is under 13, and it still agrees to keep photos); photos of a sensitive scene, of a guest and of a person under 13 are never kept. The reference is the private key of the owner's own copy and **no public response carries it**: a post says only that it has a photo, until the public copy exists. `posts`: the audience (public or followers), the state (draft, pending review, published, rejected, removed), the author's own reflection, apart from the insight and labelled as the author's text, and the times. A post the author withdraws is erased at once: its reflection, its publication, its comments, likes and bookmarks go, and only a tombstone that makes its address answer 410 remains. A post a moderator removes keeps its content, which an appeal or an audit may need, hidden from everyone, until the account is deleted. `comments`: the words of a comment or reply and its state; the author deletes their own at any time. `post_likes` and `bookmarks`: one row per account and post; who liked a post is never listed and a bookmark is private, so nothing publishes or counts them by person. `reports`: who reported what, the reason and the details they typed, the state, and the moderator's time; seen by moderators only. Nothing on the network stores an IP address: the rate limits of its writes are counters in the memory of the API process, keyed by account, and are forgotten when it restarts.

**Moderation.** The words of every reflection and every comment are sent, before anyone else sees them, to OpenAI's moderation endpoint (`omni-moderation-latest`, free of charge) so that clear cases can be published or refused at once; only the text is sent, never the account, the handle, the e-mail address or the post's other content, and OpenAI is told nothing else. This is the one flow of this kind on the network and it leaves from our servers, not from the visitor's browser. When the call cannot be made, or the answer is not clear, the text waits for a moderator and is not published. `moderation_actions`: one row for each decision (published, held, refused, removed, restored, withdrawn) with the time, who decided (the guard, a moderator, the reports or the owner), a reason code, the moderator's account id for a person's decision, and the guard's flagged category names and rounded scores. It holds the id of the post or comment but **never the text and never the author**, so it is not deleted with an account; it is a TimescaleDB hypertable that is append-only, compressed after `MODERATION_LOG_COMPRESS_AFTER_DAYS` days (30) and dropped chunk by chunk after `MODERATION_LOG_RETENTION_DAYS` days (730).

**The «لك» feed** is ranked from four facts only: how new a post is, whether the reader follows its author, whether the list already shows its topic, and whether the reader has already liked, saved or commented on it. It reads no religion, age, gender or profile answer, records nothing about what the reader opened or scrolled past, and uses no model. A reader can switch personalisation off with the personalization consent, which leaves freshness and variety only; a guest gets the same. Each item says why it is there.

## Support form

Decision 34. `POST /support` needs no sign-in and emails `SUPPORT_EMAIL` at once over the SMTP server the account mails use; no part of the message is stored in the database and no part of the message or of the visitor's address is logged (a failure logs only the kind of error). The mail carries what the visitor typed (their e-mail address, used as Reply-To, an optional name, the topic and the message) and, when a valid session cookie is present, the account id in an `X-Tabsira-Account` header (the body cannot forge it: the visitor's message is separated and every line of it quoted with "> ", under a first line saying whether the typed address is the signed-in account's verified one). The mail is marked `Auto-Submitted` and `X-Auto-Response-Suppress` so auto-responders stay quiet. It never carries the IP address, the browser's user agent or any header of the visitor's request. The route is limited in PostgreSQL, shared by every worker, and counts a message before it is sent: per client IP (an IPv6 address grouped by its /48), `SUPPORT_MAX_PER_IP_PER_HOUR`; per reply-to address, `SUPPORT_MAX_PER_ADDRESS_PER_HOUR`; and over everyone as a ceiling, `SUPPORT_MAX_PER_HOUR`. What is kept for this is one row in `login_attempts` per message, with keyed hashes of the IP and of the reply-to address (never the address itself), the kind `support` and the time; it is deleted an hour later, by the next write to the table. The route refuses a body over 16 KiB. A hidden field catches bots: a filled one is answered as if sent, and nothing is sent. When mail is not configured or the send fails the answer is 503 `mail_unavailable`, so the page never says a message was sent that was not. The mail provider that relays it is a processor of that message: it handles it in transit and in the mailbox of the support address, and the privacy page must say so. What the team keeps in that mailbox is theirs to delete on request.

## Guests

Someone who uses the app without an account gets, on the first thing they save (a scan, a kept tutorial insight), the cookie `GUEST_COOKIE_NAME` (default `__Secure-tabsira_guest`): httpOnly, Secure, SameSite=Lax, on the session cookie's domain, for `GUEST_TTL_DAYS` (90). It carries 256 random bits and an HMAC of them under the server key. `guests` stores only the SHA-256 of the random part and the times it was created and last seen (written at most once an hour), so a copy of the database cannot be turned back into a cookie. Everything below is kept under that key exactly as under an account. A guest not seen for `GUEST_TTL_DAYS` is deleted with all of it by the next guest created (there is no scheduled job). At the first sign-in from the same browser (password, sign-up or Google) the guest's scans, insights, chat, places, treasures, learner rows and exposures move to the account, places of the same region are joined, and the guest and its cookie are deleted.

## Photos and scans

- **The photo goes to the AI provider.** To understand a scene, the API sends a copy of the photo to the active AI provider (`AI_PROVIDER`: OpenAI by default, OVHcloud AI Endpoints otherwise), under that provider's terms, and to the object detector (`DETECTOR_URL`, our own service). The copy is re-encoded first, upright, with every metadata block removed (no EXIF, no GPS, no camera data), at most about one megapixel. On OpenAI the same copy also goes to its image moderation. Photos are never used for training by TABSIRA. The web app says this before a photo is sent.
- **A photo given by its address** is fetched by the API, not by the browser: public addresses and default ports only, at most three redirects, 12 seconds and 15 MB, `image/*` only, with no cookie or header of the person forwarded. The address is not stored.
- **The temporary store.** The stripped full-size copy and the model copy are kept in Redis (`REDIS_URL`) for `SCAN_IMAGE_TTL_SECONDS` (one hour) and expire on their own; the model copy is deleted as soon as the scene is understood. Each copy is sealed (AES-GCM) under a key derived from `HASH_SECRET`, which Redis never holds, so what Redis may write to its disk (snapshots, append-only file) is ciphertext that cannot be opened on that host. The owner may see the full copy again during that hour (`GET /scans/{id}/image`), and only once the sensitivity verdict has said the scene is not sensitive. A sensitive scene's photo (nudity, alcohol, drugs, gambling, violence) is deleted the moment the verdict is known and is never returned; a scan that fails before any verdict deletes both copies at once. An upload, which still carries its EXIF and GPS, is read in memory only, never spooled to a temporary file, and a body larger than the photo limit is refused before it is read. No photo is written to the database by the scan workflow; storing a photo with consent is a separate feature.
- **The GPS position** a camera wrote in the photo is read before stripping and then dropped: the scan workflow does not store it.
- `scans`: per scan, its owner, whether it came from an upload or an address, its state and outcome, the photo's pixel size, whether the scene was sensitive and which categories, the scene as understood (the model's short Arabic description, the things it named with their boxes as ratios, the actions and relations it saw, with their visible clues), what the person pointed at or drew, the one question asked and the person's answer, and the hadith the scan wanted that wait for a ruling. What the person types (a box's name, an answer) is sent to the AI provider with the scene.
- `insights`: per insight, its title, glimpse, anchor box, the verse and hadith **by reference** (surah and verse, book and number, never their text), why they were chosen, the platform's explanation, «لماذا ظهر هذا؟», the small step, its learning unit, what the person declared about the step («نفّذته» or «سأفعله لاحقًا», a statement, never a proof), and when «تمّ» was pressed. `published_at` says when the owner made the insight public, and is empty while it is private or once it was withdrawn.
- **A public insight** (v2 §18). Only a signed-in account with a verified address publishes one of its own insights (`POST /insights/{id}/publish`), and withdraws it at any time (`DELETE`, «إلغاء النشر», exempt from the legal-acceptance gate so an owner can always take their words down); a guest cannot, and neither can an account whose profile says its age is under 13 (v2 §5): such an account's published insights stop answering and leave the sitemap the moment the age is declared. The insight is refused when it is a declared simulation, when it was written for its owner in person (`why.personalised_because` set), when none of its texts is verified and shown, or when any platform text a public page prints reads like scripture. The routes follow `FEATURE_WORLD`, like the `insights` sitemap section. While it is published, `GET /public/insights/{id}` answers anyone, may be cached for five minutes, and carries: the title, the glimpse, the verse and the hadith read from the store by reference (a hadith only with an eligible ruling), the explanation parts, «لماذا ظهر هذا؟» without its personal reason, the small step, the prepared-example label, the publication time, and of the owner **only** `users.public_name` when they chose one, never the display name, the e-mail address, a profile field, a location or the account id. It never carries the chat, the learning unit, the step declaration, the completion, the scan, the place or a photo (no photo is stored yet; when photos arrive they follow the rules under «Photos»). The same address is listed in the `insights` sitemap section while the owner's account is active. A private, withdrawn, missing or another account's insight answers the same 404; so does one whose texts are no longer shown. Withdrawing deletes nothing: the insight stays its owner's.
- `insight_chat_messages`: the person's questions about an insight (at most three answered) and the answers, with the content level the model gave each question. The question, the insight's own texts and the earlier exchange of that insight are sent to the AI provider to answer; no profile field is.
- `world_places`, `world_relations`, `treasures`: the regions of the map the person opened, when they last visited each, the threads recorded between them, and the hidden treasures (a verse or hadith by reference and a learning unit) with when each was revealed.
- `evidence_exposures` (a TimescaleDB time series): per completion or revealed treasure, the verse and hadith by reference, the concept, the unit and the time, so the engine can vary the texts it shows. Not written while memory is off. Kept `EVIDENCE_EXPOSURES_RETENTION_DAYS` (730) at most.
- **What the engine is told about the person.** The goals, prior knowledge, age range and religious background they chose reach the insight engine only while personalization is on, and the texts already shown and units completed only while memory is on; the gender never does. Nothing of it reaches the scene stage, and none of it is returned except by `GET /profile`.
- **Progress (`GET /me/progress`)** is computed from the rows above on each request; nothing about it is stored. The time zone the page sends is used for that request only.
- **Operational time series**, with no owner, photo, prompt, answer or typed text: `scan_events` (each stage of a scan, its duration and how it ended, by scan id; kept `SCAN_EVENTS_RETENTION_DAYS`, 90) and `ai_calls` (each model call: provider, model, stage, attempts, tokens, cost, latency, error code; kept `AI_CALLS_RETENTION_DAYS`, 400). Once a scan is deleted its id there points to nothing.
- **Limits.** Starting a scan, answering in the chat and keeping a tutorial insight are counted per keyed hash of the IP address (never the address), in the memory of each API worker, for an hour; nothing of it is written anywhere.
- **Progress events** of a scan (its stages and outcome, no text of the person) live in Redis for `SCAN_EVENTS_TTL_SECONDS` (one hour) so a reconnecting page can catch up.
- `GET /account/export` returns all of the above that belongs to the account, without any photo; `DELETE /account` deletes it (the exposures explicitly, everything else by `ON DELETE CASCADE`) and the photos still in the temporary store.
