# Privacy: what the API stores

This is the working inventory behind the terms and privacy page. It is updated in the same change as any new data flow, and the public page must say nothing this file does not.

## Accounts

The `app` schema stores, per account and for these reasons only. `users`: the e-mail address (lower-cased; to sign in and to send the two account mails), a bcrypt hash of the password or nothing for a Google-only account, the display name, the active and admin flags, the time the address was verified, and the creation, update and deletion times. `oauth_accounts`: the provider name and Google's stable subject id, to recognise the same person next time; no Google tokens, picture or profile are kept. `sessions`: the SHA-256 hash of the session cookie's random token, the user, the creation, last-seen and expiry times, a keyed hash of the IP address (never the address) and the browser's user agent cut to 256 characters, so a person can see and end their sessions and a stolen database cannot be replayed as a cookie. `profiles`, one per account and optional: the goals, prior knowledge and age range the person chose, their religious background and gender (set in the settings only), the language, the personalization, memory and photo-storage switches, the theme, the motion preference (`system`, `on` or `off`, a display setting that follows the account to its other devices and is part of `GET /account/export`), the sound switch and the version of the consent text last answered; every unanswered field is `unknown` and nothing is inferred from a photo, a name, a place or behaviour; there is no birth date. The religious background, the gender and the age range are private: they are returned only to their owner, by `GET /profile` and `GET /account/export`, and are never written to a log. `consents`: an append-only history of each consent given or withdrawn, with its kind (`terms` for the terms of use, `privacy` for the privacy policy, and the three switches), the version of the text and the time, as the record that the person agreed. Signing up writes the `terms` and `privacy` rows at the versions accepted (decision 35); a Google sign-up keeps the versions ticked in `oauth_states` for a few minutes until the callback. `email_tokens`: the SHA-256 hash of each mailed verification or reset link token, the address it was sent to and its expiry, used once. `login_attempts`: keyed hashes of the IP address and of the e-mail address of each sign-in, sign-up and mail request, for rate limiting only, over a window of 15 minutes by default. `oauth_states`: the short-lived state of a Google sign-in in flight, valid for 10 minutes and deleted when used. Expired sessions, tokens, attempts and states are deleted by the next write to their table, not by a scheduled job, so on a quiet system an expired row can remain until then. `GET /account/export` returns everything an account owns as JSON, and `DELETE /account` deletes the account and every row above that belongs to it, sessions included.

Signing up with Google from the sign-up page needs the terms and privacy box ticked first. The tick is kept only in that tab's `sessionStorage` (the versions ticked and the time), is used once when the person comes back from Google to record the acceptance through `POST /auth/legal/accept`, and is discarded after ten minutes; it never travels in a link.

## Account mail and Google

Two flows send an address outside our servers, and only for account purposes. The API sends the verification and password-reset mails, and nothing else, through the SMTP server named by `SMTP_HOST`; that server receives the recipient's address, their display name and the link in the mail. The link carries its token after a `#`, so it appears in no web server log. Signing in with Google sends the browser to Google and receives from Google, after the person agrees, the subject id, the e-mail address with its verified flag and the name. No analytics or tracker is involved in either flow. The forgot-password and resend forms, like sign-up, sign-in and support, can load the Cloudflare Turnstile check described below.

## Cloudflare Turnstile

Installing the app (`apps/web/src/pwa/install.ts`). The browser keeps two times in its own storage and never sends them: when a first insight was done on this device (`tabsira.install.engaged`), after which the app may be offered for the home screen, and when the reader last chose «ليس الآن» (`tabsira.install.dismissed`), so the offer rests for 30 days. Installing goes through the browser's own dialog or Safari's share sheet; TABSIRA learns nothing about it and records nothing.

Decision 56. When `TURNSTILE_SITE_KEY` is set on the web server (read at request time, never baked into the build), five forms show a Cloudflare Turnstile check: sign-up, sign-in, forgot password, resend verification and the support form. On those pages only, and only then, the browser loads `https://challenges.cloudflare.com/turnstile/v0/api.js` and talks to Cloudflare, which sees the visitor's IP address and browser and device signals while the check runs; no other page loads anything from Cloudflare. The token it returns is single-use, travels in the `CF-Turnstile-Response` header of that form's request (the widget keeps no hidden input holding it), is verified by the API with Cloudflare (which also receives the visitor's IP address then, see the bot check under the support form) and is not stored. If the script cannot load, the form is refused by the API and the page says why. The signed-in «ملفي» page links to `/verify-email` for a new link instead of carrying a widget. The purpose is to stop automated abuse, not to identify anyone. With the key empty nothing is loaded and no header is sent. The privacy page names Cloudflare Turnstile, the five forms, what Cloudflare sees and why; the terms page does not mention it.

## Learning path and ontology

Two more tables of the `app` schema, and what each one keeps. `learner_unit_states`: for one account (its id) or one guest (an opaque random key the browser holds, never a name or an address) and one unit of the learning path, how many times an insight of that unit was shown, opened and completed (the person pressed «تمّ»), and the time of the first and the last of these. Completed means completed: it is not a score, a level or a measure of what the person knows or believes, and none of those is stored. «تمّ» (`POST /insights/{id}/complete`) counts a completion there, unless the person switched memory off; `GET /account/export` returns these rows, `DELETE /account` deletes them with the account (`ON DELETE CASCADE`), and a guest's rows are added to the account's at the first sign-in. `ontology_candidates`: the labels and concepts that a detector or a model proposed and that the world ontology does not hold, each with how many times it came up, which stage proposed it (detector, vision model or planner) and up to five short examples of model-written context, such as a scene description, so an editor can decide whether to add the term to a new version of the ontology. No account, session, photo, location or text typed by a person is stored in it, and a sensitive scene contributes no example.

## The insight engine and the AI provider

Before the scene leaves the scene stage, the server replaces any word that names a person by religion, age or gender (`apps/api/src/pipeline/person_words.py`: «رجل», «محجبة», «طفل», "old man" and the like) with «شخص» in every label and text and records the replacement in the scan's trace, so no such inference about anyone in the photo is stored or passed on, whatever the vision model wrote. After the scene analysis, the insight engine (`apps/api/src/pipeline/insight/`) asks the active AI provider (`AI_PROVIDER`: OpenAI or OVHcloud, as the processor named in the terms) to plan, check and explain the insights. Each of these calls carries the model-written description of the scene (its Arabic labels, actions and relations, never the photo itself, which only the scene stage receives), the answer the person typed to a clarification question when there was one, and, only while personalisation is on, the goals, prior knowledge, age range and religious background the person chose in their profile, and which of the learning-path units offered for the scene they completed; never the gender, the name, the e-mail address, the account id, the location or the photo. The concept queries the planner wrote are sent to the provider's embedding endpoint, and, with the stored texts they found, to its small rerank model (`RERANKER=llm`); neither carries anything about the person. Nothing about the person is stored by the engine: it writes only `hadith_verification_queue` (a hadith id and how many scans wanted it, for the editors), the ontology candidates described above (without an example from a sensitive scene), and `embedding_runs` (what embedding the scripture store cost, no personal data).

## Error reports

When `GLITCHTIP_DSN` is set, the API sends error reports to the GlitchTip server it names, and sends nothing when it is empty. This is the only flow of this kind, and it leaves from our servers: the visitor's browser makes no request to GlitchTip, because the web app posts its errors to the API's own `POST /client-errors`, which forwards them. A report holds the type and stack frames of the failing code, the route pattern (`GET /scripture/quran/{surah}`, never the path with its ids), the page address of a browser report, the release and environment names, the browser family (`chrome`, `firefox`, `safari` and a few others, never the full user agent), a request id and the time. Before it leaves, everything is cleaned (`docs/ERROR_TRACKING.md`): no request body, cookie, query string, `Authorization` header, address or user id; no local variables; the value of any field named like a secret, a profile field, a photo or a location is replaced; every Arabic text, so no verse, hadith, display name or typed text, is replaced; and an event raised under `/scripture` keeps only its type, frames and route. `POST /client-errors` needs no sign-in, so it stores nothing about the sender: the per-address limit counts a keyed hash of the address in the memory of the worker for five minutes and keeps it nowhere else. No account row refers to a report, so `GET /account/export` and `DELETE /account` have nothing to add for it. GlitchTip keeps reports for as long as its own retention setting says, which the operator sets and the privacy page must state.

## Cookie consent

Decision 32. The visitor chooses on the first visit, signed in or not, and the API keeps the proof of the choice in one more table of the `app` schema. `cookie_consents` holds one row per choice: a random id of the browser (`consent_id`, made by the server and kept by the browser in a first-party cookie; it is not derived from anything about the person), the version of the cookie policy the visitor was shown, whether each category was accepted (`necessary` is always true; `analytics` and `behaviour` are chosen separately), the browser family only (`chrome`, `firefox`, `safari`, `edge`, `opera`, `samsung_internet` or `other`; the database refuses anything longer or different, so no full user agent can be stored), the time, and the account id when the visitor was signed in, so the choice can be shown in «ملفي». No IP address is stored, not even hashed. The table is append-only: choosing again adds a row and the latest row of an id is the choice in force; a database trigger refuses an update, a delete and a truncate, except the delete that removes a user's rows when the user's account is deleted. `GET /account/export` lists, under `cookie_consents`, every choice made while signed in, and `DELETE /account` removes those rows with the account. Rows made while signed out carry no account and cannot be tied to a person, so the export does not list them and the deletion does not remove them.

A choice lapses, and the visitor is asked again, when `COOKIE_POLICY_VERSION` changes or after `CONSENT_REASK_DAYS` (182, six months). Until then the API reports the categories as chosen; after, only the necessary one is on and `reask` is true. The three routes, none of which needs a sign-in: `GET /consent/policy` (the policy version, the three categories with their Arabic titles and descriptions, from `src/messages.py`, and the re-ask interval), `POST /consent` (records a choice and returns the consent id with what is in force) and `GET /consent/{consent_id}` (what an id's latest choice allows now). The consent id is the only handle on a record and is unguessable (122 random bits); whoever holds it can read that choice and add another, which is why only the browser that was given it should keep it. `POST /consent` is limited per address and over all addresses, counted in the memory of each worker for five minutes and kept nowhere else, and refuses a body over 4 KiB. The responses carry `Cache-Control: no-store`. The web app's cookie for the id is itself a necessary cookie: it must hold the id and nothing else, and no analytics or behaviour tool may start before its category is accepted.

No retention period is set yet. The table is append-only by design, so nothing deletes old rows; the owners decide how long proof of consent is kept before launch, and the job that applies it must be the one thing allowed to lift the guard. The privacy page must name this table, the reasons above and that period.

In the browser, the consent uses three first-party cookies and nothing else, none readable by another site: `tabsira_consent` holds the consent id the API gave and nothing about the choice or the person, for 395 days, so the choice is found again; `tabsira_consent_dismissed` remembers, for the browser session only, a refusal the API could not record, so the question is not put on every page; `tabsira_consent_view` tells a visitor without JavaScript which view of the screen to show after the form posted (customise, or a failed save), for five minutes. To render the consent screen already open in the first paint, the web server reads `tabsira_consent` and asks the API (`GET /consent/{consent_id}`) what that id allows, once per page request; that request carries the visitor's session cookie when there is one, because a choice made while signed in is tied to the account. A form posted without JavaScript reaches the API from the web server, so those posts share the server's rate-limit budget. No analytics or behaviour script is loaded before its category is accepted, and Consent Mode starts with every category denied.

## Analytics and heatmaps

Both tools are configured on the web server (`GA_MEASUREMENT_ID`, `CLARITY_PROJECT_ID`), read at request time; empty means the tool does not exist for the visitor. Each is injected by the browser only after its category is accepted (`analytics` for Google, `behaviour` for Clarity), and neither runs on `/admin`, `/dev`, sign-in, sign-up, the mailed-link pages or `/me`.

- **Google Analytics 4** receives the page path without query string or fragment, the page title, the referrer's origin without its path, what Google itself derives from the request (browser, device, language, approximate region from the IP address), and Enhanced Measurement (scrolls, outbound clicks). Google signals and ad personalisation are off. Product events carry fixed words, counts and booleans only (typed in `apps/web/src/analytics/events.ts`; a string that is not a short lowercase word is dropped): scan started and finished, insight opened, «تمّ» pressed, share, sign-up completed, consent changed. Nothing about a person, no text, no scripture, no location. An event raised on a page where no tool runs (sign-up) waits in memory and goes out on the next page that allows one; it is never written to storage.
- **Microsoft Clarity** receives clicks, scrolls, pointer movement, screen recordings and heatmaps. The whole `<body>` carries `data-clarity-mask`, so every text, every input and every scripture or user text is masked; Clarity's advertising storage is denied.
- **Withdrawal** stops both tools at once, denies Consent Mode storage, and deletes the `_ga*`, `_gid`, `_gat*`, `_clck` and `_clsk` cookies on the host and its parent domains. A consent change is reported to Google only while analytics stays accepted.
- Google and Microsoft are recipients of these data after consent; the privacy page lists them in «ما تستلمه أدوات القياس ومتى».

## Photos

Decisions 8 and 19, and section 19 of the master prompt. This is what `apps/api/src/services/image_service.py`, `apps/api/src/storage/` and `apps/api/src/services/photo_service.py` enforce. A photo sent for analysis is not stored by that: it stays at most an hour in the temporary store described under «Photos and scans», and never for a sensitive scene. The one moment a photo is kept is the first «تمّ» (`POST /insights/{id}/complete`) of a signed-in owner on an insight of a scan whose copy is still in the temporary store: `photo_service.keep_from_buffer` re-encodes that copy and keeps it as the owner's private copy, and the insight row records the random key (`insights.photo_key`), never the image. A tutorial insight, an expired buffer, a store or Redis that cannot be reached keep nothing and the «تمّ» itself still succeeds; the only log line names the insight's id.

A photo is kept only when all of these hold, each a required argument the caller must state (`PhotoFacts`, `apps/api/src/storage/photos.py`): the `photo_storage` feature is on; the person is signed in (a guest's photo is never kept); the account has switched photo storage on (`profiles.photo_storage_consent`); the account did not say its age range is under 13 (an unanswered age is never guessed from a photo or anything else); and the scene is not sensitive. When any of them fails, the storage is not asked for anything and nothing is written. A photo is published only under the same conditions, checked again at that moment, so a photo of someone who has since said they are under 13, or withdrawn their consent, cannot be published. Withdrawing the photo consent (`POST /consents` with `granted: false`, or declaring under 13 through `PATCH /profile`) deletes both copies of every kept photo first and refuses the withdrawal with 503 `STORAGE_UNAVAILABLE` when the store cannot be reached, so a recorded withdrawal always means the photos are gone.

Before a photo is kept, its file is read once for what the camera recorded: the GPS position, its accuracy and time, and the moment the photo was taken (`CaptureMetadata`, source `photo_exif`). That is private capture metadata for the owner, who confirms or changes the place; it is not part of the stored image, and its values are left out of its printed form, so it cannot reach a log line or an error report by being printed. Then the image is re-encoded as a new JPEG, upright, at most 2560 pixels on the longer side, with no metadata at all: no EXIF, GPS, XMP, IPTC, maker note, comment, thumbnail, serial number or ICC profile (a profile is applied to the pixels, which become sRGB, and then dropped). The check in the tests looks for each of these in the bytes that are stored.

The kept copy is one private object in its owner's own folder, `private/users/<account id>/insights/<128 random bits>.jpg` (copies kept before 2026-10-05 are `private/<128 random bits>.jpg` and stay where they are), in a private S3-compatible bucket (`STORAGE_BACKEND=s3`; production requires it and refuses to start without a usable bucket, decision 44) or, on a development machine with no bucket, under `data/media` on local disk (never committed). The folder names the account, so everything one person kept can be exported or deleted together, and it is never served: deleting the account or withdrawing the photo consent deletes each photo by its row and then empties the whole folder, so no copy the rows lost track of outlives them. The random part says nothing about the photo. Its owner sees it through a link signed for `SIGNED_URL_TTL_SECONDS` (300 seconds by default, 3600 at most), and nobody else can read it. When the owner publishes a post (`POST /posts` with `photo: true`) or a map entry (`PUT /insights/{id}/map` with `photo: true`, then its publication) and chose to show the photo, the object is copied once to `public/<another random id>.jpg` (`insights.photo_public_key`), which never names the account (anyone can read that address, so it must neither expose the account id nor tie one person's published photos together), which is the only prefix served to the public, from `S3_PUBLIC_BASE_URL` (a CDN, or a bucket policy that makes `public/*` and nothing else readable). One public copy serves every publication of the insight, and only a public post or a published map entry makes it (a post for followers only never does, because `public/` is readable by anyone with the address); `photo_service.sync_public_copy` deletes it when the last public post or entry showing it is withdrawn by the owner or removed by a moderator, or when the rules above no longer hold at that change of state. When the store refuses that deletion, the person is still answered and the copy is not forgotten: the API asks the one worker process to reconcile shortly after, and an hourly command (`src/cli/reconcile_photos.py`, `photo_service.reconcile_public_copies`) deletes every public copy nothing shows any more, so the copy goes as soon as the store answers again. Placing a published map entry again (it becomes a draft), a hold by reports and a moderator's refusal after a hold delete the copy the same way. No response carries either key. The public copy's address (`photo_url`, built from `S3_PUBLIC_BASE_URL`, or from the API's own `GET /media/public/<id>.jpg` route on a development machine, which serves the `public/` prefix from the local disk and nothing else) is given only by a published public post whose owner chose the photo (`insight.photo_url`; a draft, a held post and a post for followers only say `null` even when a map entry made the copy) and by a published map entry whose owner chose it (`photo_url`); the owner's own insight view says only whether a photo is kept (`image.has_photo`). The code never marks an object public: what is readable by anyone is decided by the `public/` prefix alone, which the operator must set up and check. Private objects carry `Cache-Control: private, no-store`; published ones carry `Cache-Control: public, max-age=300`, never `immutable`, so a withdrawn or deleted photo can stay in browser and CDN caches for up to five minutes.

The S3 provider holds these objects as a processor. It sees the account id (a random UUID, not a name or an address) in the names of the private copies, in its listings and its access logs, because those copies are filed in the owner's folder; it never sees it in a published copy's name. It receives nothing else of ours: not the position, not the owner's name or e-mail address. A signed link to a private copy, should a route ever give one, names the owner's account id in its path, and is given to that owner only. `GET /account/export` lists the kept photos under `learning.photos` (the insight's id and whether a public copy exists; never a key or the image), and `DELETE /account` deletes both copies of every photo before the account row, refusing the deletion with 503 `STORAGE_UNAVAILABLE` when the store cannot be reached, so no object outlives its account (`apps/api/src/services/account_service.py`).

## The atlas

What «أطلس بصائر العالم» stores (`docs/spec/extension-atlas-camera.md` §10, `apps/api/src/models/atlas.py`). Two tables of the `app` schema keep the two locations apart. `map_capture_points` is private: the exact point the owner gave for one insight (latitude, longitude, the accuracy in metres and the time of the reading when the device gave them, where the point came from: the device at capture, the photo's EXIF, or a choice by hand) and when the owner confirmed it. Only the owner's own routes and `GET /account/export` read it; no public query joins it, and withdrawing the entry deletes it. `map_entries` is the public side: the centre of the grid cell the point fell in, computed on the server with `GEO_APPROX_CELL_METERS` when the entry is placed (never a random offset, so asking again reveals nothing), the cell size, what the point stands for (the capture point or a public place), the nearest populated place from GeoNames as a label (found from the public point, so the label hides what the cell hides), the state (draft, published, held by reports, removed by a moderator, withdrawn), the reason code of a decision and the times. A published entry is shown with its owner's public handle and name, as a post is, and only while the account is active. Withdrawing clears the public point and the place label too and leaves a tombstone so the address answers 410; an entry withdrawn before it was ever published is deleted outright, and a re-placed insight takes a new address. Public answers give the day an entry was published, never the time, and never the insight's id (a timestamp): no trail of a person's hours can be drawn from the map. A signed-in viewer never sees the entries of a member a block stands between. An account that declared itself under 13 cannot place a location. Enough reports from different accounts (`SOCIAL_REPORT_HOLD_THRESHOLD`) hide an entry until a moderator decides. The public routes return the public point alone: a test lists every field of every public schema and searches every public answer for the owner's coordinates. The browser sends the map window it shows and the filters, never the visitor's position itself: «قريب مني» moves the map on the device and sends nothing by itself; a search that follows sends the window then shown, which is centred on the device, so the page says so. Both tables belong to the account (`ON DELETE CASCADE`) and are in the export under `map_entries`. The map tiles come from OpenFreeMap (decision 9), the one third-party request a visitor's browser makes besides consented analytics; it is named on the terms and privacy pages.

What «اكتشف البصائر حولك» does in the browser (`docs/spec/extension-atlas-camera.md` §5–7, `apps/web/src/components/atlas/camera-screen.tsx`, behind the `camera_discovery` feature, read by the web server on every request). The camera is opened only after a tap, with the browser's own prompt, and is shown in a `<video>` element: no frame is drawn, read, stored or sent, and the tracks are stopped when the page is hidden or left. The position is watched on the device after the same tap and never sent as such: the page asks `GET /atlas/entries` for a window around the device widened to the atlas grid (the same coarsening as the map's window, so the API and its logs see a 0.05° cell, never the point), then measures, filters and sorts the entries on the device; it asks again only after a real move, a widening or a new centre, and ignores readings older than a minute. The orientation sensors are started by a second tap (Safari asks for permission then) and their readings stay on the device; a relative reading is never shown as a heading. Refusing the position offers a place search instead, labelled as a chosen region. Nothing of the visit is stored: no route, no heading, no position. The privacy page says the feature uses the device's position with permission and keeps no live position, and that the camera's video and the sensors' readings stay on the device, never sent, kept or analysed; it also says an account under 13 cannot place an insight on the atlas (version 2026-10-04T20:00Z, task 17.4).

«كفالة بصيرة» (decision 60, `docs/spec/DECISIONS.md`, tasks 21.1 and 21.2; the `atlas_sponsorship` feature, which needs the atlas). `map_entries.last_active_at` records the last sign of life of an entry: its publication, its author's placing it again, a sponsorship starting, the sponsor writing their reflection. A view never sets it and nothing is recorded about readers; on the migration every entry starts at the time of the migration, so nothing is orphaned retroactively. A daily job (`python -m src.cli.mark_orphans`, one host, hardened systemd unit) turns a published entry with no sponsorship and no sign of life for `ORPHAN_AFTER_DAYS` (30) into `orphaned`, and in the same transaction widens its public place for good. The level is chosen from the area alone, never from how far its centre is from the earlier public point (that distance would betray the hidden point), and only among levels whose cell is larger than the entry's own: the region (GeoNames ADM1) of the place it was labelled with when the region has 100 000 people or more; else that place when it is a city of 10 000 or more; else the country centre; else a fixed grid cell, the first of 50, 100, 200 km and larger that is at least twice the entry's own cell. The private capture point is never read by the job. `map_entries.widened_level` holds the level and is never cleared, the public point, the cell size and the labels become the widened area's, the photo is no longer shown, and every public answer drops the author's handle and name and the link to their post (a separate public post of the same insight in the network still names its author, which the terms say). The entry is given a new public id when it is widened, since the old one is the millisecond it was placed; `map_entry_retired_ids` keeps the old id so that it answers 410, with nothing that leads to the new one, and the rows that name the entry (capture point, generalisation, sponsorship, reports) follow the change (`ON UPDATE CASCADE`). A block against the hidden author changes no answer, since it would name the author; a block against the sponsor hides the entry. `map_entry_generalisations` keeps one row per widening: the earlier public point, cell size and place label, the new level and label, the reason (`orphaned`) and the time. No route, public or admin, reads it (a test searches every public answer for it); the author's own view and export carry the level, label and time only; it is deleted when the author withdraws the entry. Placing the entry again by its author moves their private point only; the public place stays widened. `map_entry_sponsorships` holds, per entry, the sponsor and the sponsor's one reflection with its state; it exists only while the sponsorship does (ending it, the author withdrawing, a moderator removing the entry or the sponsor deleting the account deletes the row). The sponsor chose to sponsor in public: their handle and public name appear beside the entry, and so does the reflection once the comment guard has published it (words that read like the Quran or a hadith are refused). A reflection can be reported and is moderated in the queue like a comment, and its decisions are in the moderation log. `GET /account/export` lists the account's sponsorships under `sponsorships`. `GET /atlas/orphans?lat=&lng=&radius=` receives a position for that one request, snaps it on the server to a grid of about 0.05 degrees before any use, stores nothing of it, answers `no-store`, and the API's nginx access log for `/atlas/` records the path without the query string and without the referer. The widening protects against people who never saw the entry: someone who saw it before it was widened can still match it by its title and texts, which are not changed, and a separate public post of the same insight still names its author. Atlas pages of a widened entry carry `noindex`. nginx's error log (not the access log) may still hold the query string of a request that failed with a 502 or 504; error logs are short-retention operations logs, read by the operators alone. Terms and privacy text changed with this flow (version 2026-10-05T16:00Z).

## Admin area

Who may sign in, what they can see, and what is written down about them (`docs/ADMIN.md`). Three tables of the `app` schema. `admin_sessions`: one row per signed-in admin browser, with the SHA-256 hash of the cookie's random token, the account, the creation, last-seen and expiry times (twelve hours, never extended), a keyed hash of the IP address (never the address) and the user agent cut to 256 characters; deleted when it expires, when the admin signs out and with the account. `admin_totp`: the second factor of an admin, with the shared secret **encrypted** under `ADMIN_TOTP_ENCRYPTION_KEY` (a copy of the table is useless without the key), ten recovery codes as keyed hashes, when the factor was switched on and the step of the last accepted code so that a code works once; deleted when the admin switches it off and with the account. `admin_audit_log`: one row for every admin sign-in, failed sign-in and sign-out, every list page, record page, create, edit, delete and bulk action, every second-factor change, and every grant or revoke of admin rights done on the command line; a row holds the time, the admin's account id (for a failed sign-in, the account the attempt named, when it matched one), the action, the view and record id, a small JSON, a keyed hash of the IP address and the user agent. The JSON holds only the names of the fields that changed, a reason code and the ids a bulk action touched with their count: never what was typed, never a search word, never the e-mail address entered at a failed sign-in. The log is a TimescaleDB hypertable partitioned on its time column. It is append-only (a trigger refuses every update and delete), compressed after `ADMIN_AUDIT_COMPRESS_AFTER_DAYS` (30 by default) and dropped after `ADMIN_AUDIT_RETENTION_DAYS` (400 by default). Its account and record ids are plain columns with no foreign key: deleting an account does not delete its rows from the log, which keep an id that names nobody until the retention drops them, as the record of what an admin did.

What an admin sees of a person: the e-mail address, the display name, whether the account is active, an admin and verified, when it was created, updated and (if deleted) deleted, the consents given and withdrawn, and the browser's user agent of each session. An admin can rename an account, switch it on or off and end its sessions. An admin never sees a profile (religious background, gender, age range, goals, knowledge level), a password hash, a session token, a second-factor secret or recovery code, a photo or a location, and the admin area has no export: no CSV or JSON copy of this data can be made from it. Only a person with an account that has `is_admin` can sign in, with a password and, once enrolled, a code; admin rights are given and taken only on the server's command line.

## The social network

What «تبصرة تواصل» stores and shows (`docs/SOCIAL_NETWORK.md`). Everything below belongs to one account, is returned to its owner by `GET /account/export` (the `social` object) and is deleted with the account, except the moderation log. `users.handle` and `users.public_name`: the handle and the name the person chose to be known by on the network, both empty until they choose; they are the **only** things a public page says about a person, besides the month the account was created and three counts. The account's own display name, the e-mail address, the profile answers and any location are never in a public response, a feed, a comment or the sitemap, and the public name is never copied from the account's own name. `follows` and `blocks`: who follows and who blocked whom, with the time; a block is visible to its owner alone, and the blocked person is answered as if the other did not exist. `insight_publications`: the copy of a verified insight that a post publishes, made once and never edited (the database refuses an update): the platform's title, glimpse, explanation excerpt and small step, the insight's id and version, and **references** to the evidence (surah and ayah, book and hadith number), never scripture, which a reader's response reads from the scripture store. It keeps a photo reference only if the owner consented to publish the photo, the scene is not sensitive and the photo rules above still allow it at that moment (the feature is on, the account has not since said it is under 13, and it still agrees to keep photos); photos of a sensitive scene, of a guest and of a person under 13 are never kept. The reference is the private key of the owner's own copy and **no public response carries it**: a post says only that it has a photo, until the public copy exists. `posts`: the audience (public or followers), the state (draft, pending review, published, rejected, removed), the author's own reflection, apart from the insight and labelled as the author's text, and the times. A post the author withdraws is erased at once: its reflection, its publication, its comments, reactions and bookmarks go, and only a tombstone that makes its address answer 410 remains. A post a moderator removes keeps its content, which an appeal or an audit may need, hidden from everyone, until the account is deleted. `comments`: the words of a comment or reply and its state; the author deletes their own at any time. `post_reactions` and `bookmarks`: a reaction is one row per account, post and kind («انتفعتُ بها» or «جزاك الله خيرًا»), a bookmark one row per account and post; the number of each kind of reaction is public, but who reacted is never listed, and a bookmark is private, so nothing publishes or counts either by person. `reports`: who reported what, the reason and the details they typed, the state, and the moderator's time; seen by moderators only. Nothing on the network stores an IP address: the rate limits of its writes are counters in the memory of the API process, keyed by account, and are forgotten when it restarts.

**Moderation.** The words of every reflection and every comment are sent, before anyone else sees them, to OpenAI's moderation endpoint (`omni-moderation-latest`, free of charge) so that clear cases can be published or refused at once; only the text is sent, never the account, the handle, the e-mail address or the post's other content, and OpenAI is told nothing else. This is the one flow of this kind on the network and it leaves from our servers, not from the visitor's browser. When the call cannot be made, or the answer is not clear, the text waits for a moderator and is not published. `moderation_actions`: one row for each decision (published, held, refused, removed, restored, withdrawn) with the time, who decided (the guard, a moderator, the reports or the owner), a reason code, the moderator's account id for a person's decision, and the guard's flagged category names and rounded scores. It holds the id of the post or comment but **never the text and never the author**, so it is not deleted with an account; it is a TimescaleDB hypertable that is append-only, compressed after `MODERATION_LOG_COMPRESS_AFTER_DAYS` days (30) and dropped chunk by chunk after `MODERATION_LOG_RETENTION_DAYS` days (730).

**The «لك» feed** is ranked from four facts only: how new a post is, whether the reader follows its author, whether the list already shows its topic, and whether the reader has already reacted to, saved or commented on it. It reads no religion, age, gender or profile answer, records nothing about what the reader opened or scrolled past, and uses no model. A reader can switch personalisation off with the personalization consent, which leaves freshness and variety only; a guest gets the same. Each item says why it is there.

## Public insights

An insight is public only when its owner publishes it (`PUT /insights/{id}/publication`) and stops being public the moment they withdraw it (`DELETE` on the same path). `insights.published_at` is set while it is public and `insights.withdrawn_at` keeps the last time it was taken down; both are the owner's own history, are returned by `GET /account/export` with the insight and are deleted with the account. Publishing needs a signed-in account with a verified e-mail address (decision 25), the same rate limit as a post, and is switched off with the `world` feature; a guest's insight is never public (a database constraint), and an account whose profile says its age range is under 13 cannot publish an insight at all (`409 UNDER_13_CANNOT_PUBLISH`), a declared answer the person can change, never something inferred. Withdrawing needs only the signed-in owner: no verified address, no acceptance of a newer text and no feature flag, because it publishes nothing.

Publishing is refused (409) for an insight that did not come out of the real analysis (a `prepared` example or a `demo` simulation, the rule a post follows), whose scene is sensitive, that was shaped by the profile (`why.personalised_because` is set), that has no verse or eligible hadith to show from the store, or whose title, glimpse, explanation or small step looks like scripture. That last check is the one the analysis applies to what a model wrote (`src/scans/accept.py`, `leaks`): the pattern rules, a run of words of the cited texts, and a run of words of any verse or hadith of the store.

`GET /public/insights/{id}` answers anyone, with no sign-in and no cookie, and nothing it sets or reads identifies the visitor. An insight that is unpublished, withdrawn, a guest's, owned by a closed or deleted account, with no verse or eligible hadith to show now (a ruling may have changed since), or unknown answers the same 404, and every answer carries `Cache-Control: no-store` so a withdrawal shows at once. The answer holds: the title, the glimpse, the relation, the verse and the hadith read from the store byte for byte with their stored hashes (a hadith only while it is eligible, decisions 18 and 58), the platform's explanation without its «ما ظهر» part and its small step (those resting on a hidden text are dropped), the publication time, and the author only as the public handle and public name the owner chose for the network, or nothing when they chose none. It never holds the photo or its address, the scan, the box on the photo, any place or location (exact or approximate), the chat, the declared action, completion, the learning unit, «لماذا ظهر هذا؟» (its clues, its limits, the reason of a personal choice), the engine's reason for a text (`why`, `matched_on`), the account's id, e-mail address, display name or profile. No photo is part of a public insight: the scan keeps none (see Photos and scans), so the consent rules for a published photo have nothing to apply to until a stored photo exists.

**The share card.** `GET /insights/{id}/card` on the web app draws, for anyone and at each request, a PNG of a public insight from `GET /public/insights/{id}` alone: the title, the verse and the hadith with their references and the hadith's ruling, the notice of a hadith awaiting its ruling, the author only as the public handle and name the owner chose, the app's name and address and the AI disclosure. It holds no photo, no place and no metadata of any kind. It is not stored beyond a short in-process memory of the last cards drawn, keyed by the content of the API's answer (nothing is written to disk and a restart forgets it); the API is asked at every request, so once the owner withdraws the insight the card answers the same 404 as the page, with `Cache-Control: no-store`. A copy already downloaded stays with whoever has it. At most two cards are drawn at a time in each web process, the rest wait briefly or are told to retry (503), and nginx limits the requests per address.

## Bot check

Decision 56. When `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY` are set, `POST /auth/signup`, `/auth/login`, `/auth/forgot-password`, `/auth/resend-verification` and `POST /support` ask for a Cloudflare Turnstile token in the `CF-Turnstile-Response` header. The API sends the token and the visitor's IP address to Cloudflare (`challenges.cloudflare.com/turnstile/v0/siteverify`) to check it, and nothing else; the token and the address are never logged or stored, only the error codes Cloudflare answers with. A missing, refused or unverifiable token is refused with 403 `turnstile_failed` before anything is counted or written. With both keys empty the check is off and nothing is sent. The widget the browser loads from Cloudflare is described in the privacy page of the web app.

## Support form

Decision 34. `POST /support` needs no sign-in and emails `SUPPORT_EMAIL` at once over the SMTP server the account mails use; no part of the message is stored in the database and no part of the message or of the visitor's address is logged (a failure logs only the kind of error). The mail carries what the visitor typed (their e-mail address, used as Reply-To, an optional name, the topic and the message) and, when a valid session cookie is present, the account id in an `X-Tabsira-Account` header (the body cannot forge it: the visitor's message is separated and every line of it quoted with "> ", under a first line saying whether the typed address is the signed-in account's verified one). The mail is marked `Auto-Submitted` and `X-Auto-Response-Suppress` so auto-responders stay quiet. It never carries the IP address, the browser's user agent or any header of the visitor's request. The route is limited in PostgreSQL, shared by every worker, and counts a message before it is sent: per client IP (an IPv6 address grouped by its /48), `SUPPORT_MAX_PER_IP_PER_HOUR`; per reply-to address, `SUPPORT_MAX_PER_ADDRESS_PER_HOUR`; and over everyone as a ceiling, `SUPPORT_MAX_PER_HOUR`. What is kept for this is one row in `login_attempts` per message, with keyed hashes of the IP and of the reply-to address (never the address itself), the kind `support` and the time; it is deleted an hour later, by the next write to the table. The route refuses a body over 16 KiB. A hidden field catches bots: a filled one is answered as if sent, and nothing is sent. When mail is not configured or the send fails the answer is 503 `mail_unavailable`, so the page never says a message was sent that was not. The mail provider that relays it is a processor of that message: it handles it in transit and in the mailbox of the support address, and the privacy page must say so. What the team keeps in that mailbox is theirs to delete on request.

## Guests

Someone who uses the app without an account gets, on the first thing they save (a scan, a kept tutorial insight), the cookie `GUEST_COOKIE_NAME` (default `__Secure-tabsira_guest`): httpOnly, Secure, SameSite=Lax, on the session cookie's domain, for `GUEST_TTL_DAYS` (90). It carries 256 random bits and an HMAC of them under the server key. `guests` stores only the SHA-256 of the random part and the times it was created and last seen (written at most once an hour), so a copy of the database cannot be turned back into a cookie. Everything below is kept under that key exactly as under an account. A guest not seen for `GUEST_TTL_DAYS` is deleted with all of it by the next guest created (there is no scheduled job). At the first sign-in from the same browser (password, sign-up or Google) the guest's scans, insights, chat, places, reveals, treasures, learner rows and exposures move to the account, places of the same region are joined (a guest's reveal of a concept the account already has is dropped; one whose slot the account already holds is dropped and made again from the moved insights in a free slot), and the guest and its cookie are deleted.

## Photos and scans

- **The photo goes to the AI provider.** To understand a scene, the API sends a copy of the photo to the active AI provider (`AI_PROVIDER`: OpenAI by default, OVHcloud AI Endpoints otherwise), under that provider's terms, and to the object detector (`DETECTOR_URL`, our own service). The copy is re-encoded first, upright, with every metadata block removed (no EXIF, no GPS, no camera data), at most about one megapixel. On OpenAI the same copy also goes to its image moderation. Photos are never used for training by TABSIRA. The web app says this before a photo is sent.
- **A photo given by its address** is fetched by the API, not by the browser: public addresses and default ports only, at most three redirects, 12 seconds and 15 MB, `image/*` only, with no cookie or header of the person forwarded. The address is not stored.
- **The temporary store.** The stripped full-size copy and the model copy are kept in Redis (`REDIS_URL`) for `SCAN_IMAGE_TTL_SECONDS` (one hour) and expire on their own; the model copy is deleted as soon as the scene is understood. Each copy is sealed (AES-GCM) under a key derived from `HASH_SECRET`, which Redis never holds, so what Redis may write to its disk (snapshots, append-only file) is ciphertext that cannot be opened on that host. The owner may see the full copy again during that hour (`GET /scans/{id}/image`), and only once the sensitivity verdict has said the scene is not sensitive. A sensitive scene's photo (nudity, alcohol, drugs, gambling, violence) is deleted the moment the verdict is known and is never returned; a scan that fails before any verdict deletes both copies at once. An upload, which still carries its EXIF and GPS, is read in memory only, never spooled to a temporary file, and a body larger than the photo limit is refused before it is read. No photo is written to the database by the scan workflow; keeping a photo with consent happens at «تمّ» and is described under «Photos».
- **The GPS position** a camera wrote in the photo is read before stripping and then dropped: the scan workflow does not store it.
- `scans`: per scan, its owner, whether it came from an upload or an address, its state and outcome, the photo's pixel size, whether the scene was sensitive and which categories, the scene as understood (the model's short Arabic description, the things it named with their boxes as ratios, the actions and relations it saw, with their visible clues), what the person pointed at or drew, the one question asked and the person's answer, and the hadith the scan wanted that wait for a ruling. What the person types (a box's name, an answer) is sent to the AI provider with the scene.
- `insights`: per insight, its title, glimpse, anchor box, the verse and hadith **by reference** (surah and verse, book and number, never their text), why they were chosen, the platform's explanation, «لماذا ظهر هذا؟», the small step, its learning unit, what the person declared about the step («نفّذته» or «سأفعله لاحقًا», a statement, never a proof), and when «تمّ» was pressed.
- `insight_chat_messages`: the person's questions about an insight (at most three answered) and the answers, with the content level the model gave each question. The question, the insight's own texts and the earlier exchange of that insight are sent to the AI provider to answer; no profile field is.
- `world_places`, `world_relations`, `treasures`: the regions of the map the person opened, when they last visited each, the threads recorded between them, and the hidden treasures (a verse or hadith by reference and a learning unit) with when each was revealed.
- `world_reveals` (decision 59): per learning unit the person completed (or per insight without one), the circle of the world picture it lifted from the clouds (the region, the layout version and slot, the position and radius as ratios of the picture, the drawing's theme), the first insight that learned it, when it was learned, and when the world first showed it (for what was learned before reveals existed, when the reveal was made, so no effect plays for it). Derived from the completions alone; nothing about the photo or a place on Earth.
- `evidence_exposures` (a TimescaleDB time series): per first display of an insight's texts to their owner, per completion and per revealed treasure, the verse and hadith by reference, the concept, the unit and the time, so the engine can vary the texts it shows. Not written while memory is off. Kept `EVIDENCE_EXPOSURES_RETENTION_DAYS` (730) at most.
- **What the engine is told about the person.** The goals, prior knowledge, age range and religious background they chose reach the insight engine only while personalization is on, and the texts already shown and units completed only while memory is on; the gender never does. Nothing of it reaches the scene stage, and none of it is returned except by `GET /profile`.
- **Progress (`GET /me/progress`)** is computed from the rows above on each request; nothing about it is stored. The time zone the page sends is used for that request only.
- **Operational time series**, with no owner, photo, prompt, answer or typed text: `scan_events` (each stage of a scan, its duration and how it ended, by scan id; kept `SCAN_EVENTS_RETENTION_DAYS`, 90) and `ai_calls` (each model call: provider, model, stage, attempts, tokens, cost, latency, error code; kept `AI_CALLS_RETENTION_DAYS`, 400). Once a scan is deleted its id there points to nothing.
- **Limits.** Starting a scan, answering in the chat and keeping a tutorial insight are counted per keyed hash of the IP address (never the address), in the memory of each API worker, for an hour; nothing of it is written anywhere.
- **Progress events** of a scan (its stages and outcome, no text of the person) live in Redis for `SCAN_EVENTS_TTL_SECONDS` (one hour) so a reconnecting page can catch up.
- `GET /account/export` returns all of the above that belongs to the account, without any photo (the kept photos are listed by insight under «Photos»); `DELETE /account` deletes it (the exposures explicitly, everything else by `ON DELETE CASCADE`), the photos still in the temporary store and the kept photos in object storage.
